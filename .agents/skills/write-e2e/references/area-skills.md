# Delegating to an area skill

Some areas of `test/new-e2e/tests/` own their own template and lifecycle rules through a directory-scoped skill (`test/new-e2e/tests/<area>/.claude/skills/*/SKILL.md`). When one exists, it writes the test for the assertions it covers, in place of Steps 2 to 8, and this skill keeps Step 9 and the Output. Follow these steps in order.

1. **Check what it writes.** Read its description, its `argument-hint`, the checks it makes on its argument, and the assertions its template prescribes. Delegate only when those assertions are the selected ones, no fewer and no more, and when the environment and OS its template provisions honor the constraints of the request (`--env`, `--os`, or stated in words): a skill adding checks the gate dropped widens the scope past the audit, and one skipping some leaves them uncovered. `write-agent-health-e2e`, for example, takes one existing issue module under `comp/healthplatform/issues/` and asserts both its detection and its resolution, with their payload fields. It fits a selection holding that module's detection and resolution on its default Linux host, but not a selection with only its detection, a service-restart assertion in the same area, or `--os windows`. When it doesn't fit, follow Steps 2 to 9 here instead, reading the area skill for the area's conventions.
2. **Invoke it** by its `name`, with exactly the argument its `argument-hint` names and nothing else: `write-agent-health-e2e` reads its whole argument as the module directory, so `rofspermissions`, not the assertions. Keep the delegated assertions, their verdict reasons and hops here, to check its result against. Never pass the original request, which still holds the assertions the gate dropped. Directory-scoped skills are only offered when the working directory matches, so read the file directly and follow it when it is not in the skill list.
3. **Stop it once the test is written.** Follow it until its files are written, and run none of its verification commands: they replace Step 9's, in another order. `write-agent-health-e2e` runs its suite right after lint, which would provision infrastructure before G2's dependency scan and G3's CI wiring, and its lint omits `--module=test/new-e2e`, so it lints the root module rather than the test's.
4. **Run Step 9 on what it wrote.** Run G1 to G5 in order, filtered to the suite it wrote (`--run '^TestX$'`), with Step 9's approval rule: show each command that provisions cloud infrastructure and get agreement before running it. Stop at the first failure.
5. **Report per assertion.** Write this skill's Output from its result. In `Scope`, give each delegated assertion its test (file and test name) and its validation: `validated` only when every Step 9 gate passed with that test, otherwise **written, not validated** (the gates that didn't run or failed, and the targeted run that passed, if any) or **incomplete** (no test, with the reason). Take `Files` from the files it created or modified, and `Local run` from the Step 9 gates run, with their results. List under `Follow-ups` each Step 9 gate still not run, as a gap.
